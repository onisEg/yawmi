## 1) المشروع ده بيعمل إيه؟

**يومي** هو تطبيق عربي لإدارة الحياة اليومية، يربط بين العبادات والعادات والمهام والأهداف والمصاريف واليوميات والتحديات والإحصائيات. الفكرة: المستخدم يسجّل يومه بسرعة ويراجع تقدمه على فترات مختلفة.

المحاور الأساسية:
- **اليوم:** صلوات، عادات، أذكار، مزاج، نوم، قرآن، يوميات، نتيجة اليوم.
- **المهام:** مواعيد، أولويات (مهم/عاجل)، مشاريع، ترتيب، بحث وسلة محذوفات.
- **الأهداف والمشاريع:** أهداف كبيرة، مشاريع مرتبطة بها، وتقدّم محسوب من المهام.
- **المصاريف والالتزامات:** إدخال المصروفات، تصنيفات، ميزانيات، ديون والتزامات.
- **الملاحظات:** بحث، تثبيت وتلوين.
- **التحديات:** جاهزة ومخصّصة، مع تتبّع تقدّمها.
- **نظرة/الإحصائيات:** مراجعة أسبوعية، تقويم، تاريخ وإحصائيات.
- **الحساب والإعدادات:** وضع فاتح/غامق، خط عربي وحجمه، PIN محلي، نسخ احتياطي ومزامنة اختيارية.

> **حدود التوثيق:** ده مبني على قراءة `README.md` و`index.html` و`manifest.json` و`sw.js`. مش تقرير اختبار شامل للتطبيق أثناء التشغيل، ولا فحص لإعدادات Supabase الخارجية. وجود ميزة في الكود لا يضمن نجاح كل سيناريو لها.

## 2) التقنيات

| التقنية | دورها |
|---|---|
| HTML5 | بنية واجهة المستخدم |
| CSS3 / CSS variables / Media Queries | الـthemes والتصميم المتجاوب |
| Vanilla JavaScript | الأحداث، الحالة، حساب الإحصائيات وعرض الواجهات |
| LocalStorage | تخزين محلي للبيانات والإعدادات |
| Supabase JS v2 | Auth ومزامنة بيانات المستخدم |
| Service Worker | كاش ملفات التطبيق وتشغيل الواجهة أوفلاين |
| Web App Manifest | التثبيت والأيقونات والاختصارات |
| GitHub Pages | الاستضافة المذكورة في README |
| Aladhan API | جلب مواقيت الصلاة |
| `Intl.DateTimeFormat` | تنسيق التاريخ والتقويم الهجري (Umm al-Qura) |

**مهم:** الريبو الحالي لا يعتمد على React/Vue، ولم نجد `package.json` في جذر المشروع. مكتبة Supabase تُحمّل في `index.html` عبر ES module من CDN أساسي وبديل.

## 3) معمارية النسخة الحالية

الملفات الأساسية المؤكدة:

```text
yawmi/
├── index.html       # HTML + CSS + JavaScript في ملف رئيسي ضخم
├── manifest.json    # تعريف PWA واختصارات التطبيق
├── sw.js            # Service Worker والكاش
├── README.md        # وصف المنتج وتعليمات الاستخدام
└── ...              # صور وأيقونات وملفات مساعدة
```

ملف `index.html` وقت المراجعة حوالي **10,065 سطر** و**493 KB نصيًّا**. ده **technical debt** وليس بالضرورة خطأ وظيفي: تعديل جزء ممكن يؤثر على جزء آخر، وصعب اختباره ومراجعته بمعزل عن باقي التطبيق.

التدفق العام:

```text
Browser
  ├─ index.html: UI / CSS / Events
  ├─ Application state in JS
  │    └─ load(...) / store(...)
  │          └─ LocalStorage
  ├─ Supabase Auth
  │    └─ syncPull() / merge / syncPush() → yawmi_data
  ├─ Aladhan API (network-dependent)
  └─ Service Worker (sw.js) → Cache Storage
```

الواجهات تتبدّل من داخل الصفحة نفسها؛ مش routing مبني على framework. بعض دوال رسم الشاشات المؤكدة: `renderToday()` و`renderTasks()` و`renderGoals()` و`renderExp()` و`renderNotes()` و`renderDash()`.

## 4) تشغيل المشروع محليًا

```bash
git clone https://github.com/onisEg/yawmi.git
cd yawmi
python -m http.server 5500
```

افتح `http://localhost:5500` من المتصفح. ممكن استخدام VS Code + Live Server بدل Python.

- شغّل من `localhost` أو HTTPS عشان Service Worker يشتغل.
- الوظائف المحلية متاحة بدون حساب في الظروف المعتادة.
- المزامنة ومواقيت الصلاة المباشرة تحتاج اتصال بالخدمة الخارجية.
- لا تغيّر بيانات المستخدم الحقيقية أثناء تجربة سيناريوهات المزامنة؛ استخدم **حسابًا تجريبيًا** وبيانات تجريبية.

## 5) نموذج البيانات الحالي (LocalStorage)

التطبيق يستخدم مفاتيح منفصلة. من الكود:

```js
const K = {
  days: 'yawmi_days',
  tasks: 'yawmi_tasks',
  exp: 'yawmi_exp',
  obl: 'yawmi_obl',
  rev: 'yawmi_rev',
  goals: 'yawmi_goals',
  bh: 'yawmi_bhdata',
  set: 'yawmi_settings',
  notifs: 'yawmi_notifs',
  challenges: 'yawmi_challenges',
  notes: 'yawmi_notes'
};
```

مفاتيح أخرى موجودة خارج `K`، مثل `yawmi_reminders` و`yawmi_ptimes` و`yawmi_premerge_backup`. **ما تفترضش إن كل مفتاح محلي بيتزامن**: في الكود، `SYNC_KEYS` تشمل الأيام والمهام والمصاريف والالتزامات والمراجعات والأهداف والعادات السلبية والإعدادات، بينما `collectAllData()` تجمع أيضًا التحديات والملاحظات. لازم نتحقق من كل المسارات قبل أي إعادة تنظيم.

**النمط الحالي:**
- `load(k, fallback)`: يقرأ JSON من LocalStorage، ويرجع fallback عند عدم وجود القيمة أو خطأ في parsing.
- `store(k, value)`: يضيف timestamp لبعض العناصر، يحفظ JSON، ويستدعي مزامنة قريبة لبعض المفاتيح.
- `stampItems(k, value)`: يحدّث `updatedAt` للعناصر المعدّلة في مصفوفات معيّنة مثل المهام والمصاريف.
- `saveDays()`: يحفظ اليوم الحالي، مع `u = Date.now()` لمتابعة وقت تحديث اليوم.

**تنبيه:** LocalStorage مش قاعدة بيانات مشفّرة، ومسح بيانات المتصفح قد يفقد البيانات غير المتزامنة. جرّب التصدير والاستيراد بانتظام، خصوصًا قبل أي Refactor.

## 6) حساب نتيجة اليوم

الدالة الفعلية: `scoreOf(d)` داخل `index.html`.

- 5 نقاط كحد أقصى للصلوات، بناءً على عدد الصلوات المسجّلة بحالة truthy من أصل خمس.
- 5 نقاط كحد أقصى للعادات، بناءً على عدد العادات المنجزة من إجمالي العادات المحدّدة.
- الناتج يُقرّب لمنزلة عشرية واحدة.

```js
function scoreOf(d) {
  const pr = d.p.reduce((a, b) => a + (b ? 1 : 0), 0);
  const hs = settings.habits;
  const hd = hs.filter(h => d.h[h]).length;
  const pScore = (pr / 5) * 5;
  const hScore = hs.length ? (hd / hs.length) * 5 : (pr / 5) * 5;
  return Math.round((pScore + hScore) * 10) / 10;
}
```

**مثال:** 4/5 صلوات و3/4 عادات → 4 + 3.75 = **7.8/10**.

**Edge case:** لو مفيش عادات، درجة العادات بتساوي درجة الصلوات، فتبقى الدرجة كلها مبنية على الصلوات. ده قرار حالي في الكود؛ ينبغي تثبيته باختبار ومراجعته باعتباره قرار منتج.

**ملاحظة أخرى:** كل حالة صلاة غير صفرية بتتحسب بنفس الوزن عند حساب النتيجة؛ لو المقصود التمييز بين الحالات لازم نعدّل المعادلة بقرار واضح، مش بالصدفة أثناء الـRefactor.

## 7) تفاصيل الوحدات (Feature Modules)

### 7.1 Daily & Prayer
- اختيار اليوم والتنقّل بين الأيام.
- عرض التاريخ الميلادي والهجري.
- حالات الصلاة ومؤقت الصلاة القادمة.
- متابعة العادات، الأذكار، القرآن، المزاج، النوم واليوميات.
- كروت وتذكيرات لأعمال أو مناسبات دينية.
- **اعتماد خارجي:** بيانات مواقيت الصلاة، مع تخزين محلي لبيانات سبق تحميلها.
- **تحقق مهم:** دقة التوقيت والمنطقة الزمنية، ودقة المناسبات الهجرية (قد تختلف الرؤية ± يوم بحسب البلد).

### 7.2 Tasks
- `renderTasks()` يعرض مجموعات زمنية وأولويات.
- دعم مهام مرتبطة بمشاريع، بحث وترتيب وحذف/استرجاع.
- **تحقق مهم:** تسلسل الأولويات، انتهاء المواعيد، مزامنة الحذف، وعدم ظهور مهام محذوفة بعد الدمج.

### 7.3 Goals & Projects
- `renderGoals()` و`goalPct(g)` لتحديث عرض الأهداف.
- `goalPct` يحسب **متوسط** `pct` للمشاريع؛ لا يزن المشاريع حسب حجمها.
- **تحقق مهم:** مشروع بلا مهام، هدف بلا مشاريع، حذف المهام، وعرض نسبة التقدم بعد المزامنة.

### 7.4 Expenses & Obligations
- `renderExp()` والمكونات ذات الصلة تعرض المصاريف والالتزامات.
- الدخل، تصنيفات وموازنات، عملة، التزامات ومديونيات.
- **تحقق مهم:** حدود الميزانية، المدفوعات المتكررة، تكرار الإدخالات بعد المزامنة، الكسور والعملات، وتغيّر الشهور/السنة.

### 7.5 Notes & Journaling
- `renderNotes()`: بحث وتثبيت وترتيب.
- `saveNotes()` يحفظ الملاحظات محليًا.
- **تحقق مهم:** المحتوى الغني/HTML، الحذف والاسترجاع، حجم النص، وتعارض الملاحظات بين الأجهزة.

### 7.6 Challenges & Insights
- تحديات جاهزة مرتبطة بالتسجيل الفعلي، ومخصصة.
- تقارير/إحصائيات ومراجعة أسبوعية.
- **تحقق مهم:** عدم احتساب التقدم مرتين، تواريخ بدء/نهاية التحديات، والتقويم مع الأيام غير المسجّلة.

## 8) تسجيل الدخول والمزامنة

عميل Supabase يُنشأ باستخدام **publishable key** مخصص للواجهة العامة؛ ظهوره في Frontend **مش سرًا بحد ذاته**. الأمان الحقيقي يعتمد على إعدادات Auth والصلاحيات و**Row Level Security (RLS)** في Supabase، ودي **لم يتم فحصها** في هذه المراجعة.

المسارات المهمة:
- `initSupabase()`: إنشاء عميل Supabase وقراءة/تحديث حالة الجلسة.
- `collectAllData()`: جمع وحدات البيانات في كائن واحد.
- `syncPull()`: قراءة `data, updated_at` من `yawmi_data` للمستخدم الحالي.
- `syncPush()`: `upsert` لبيانات المستخدم الحالية في `yawmi_data`.
- `syncFull()`: تنسيق السحب والدمج والرفع، مع تجنّب الرفع إذا تعذّر السحب.
- `mergeDay()` ومنطق الدمج المجاور: حل تعارضات التعديلات؛ يُفضّل اختباره بشدة.
- `localSafetyBackup()`: يحفظ snapshot في `yawmi_premerge_backup` قبل الدمج.

### سيناريوهات اختبار ضرورية

1. جهاز A يضيف مهمة أوفلاين، وجهاز B يضيف مهمة ثانية → عند الاتصال يظهر الاثنان.
2. جهاز A يعدّل مهمة وجهاز B يحذفها → نتيجة محدّدة ومتّسقة، بدون عودة العنصر المحذوف.
3. تعديل نفس الصلاة/العادة على جهازين → آخر تعديل وفق السياسة الواضحة؛ اختبار `mergeDay()`.
4. فصل الإنترنت لحظة بدء `syncFull()` → مفيش رفع بيانات ناقصة فوق السحابة.
5. سحب/رفع يفشل أو تنتهي الجلسة → رسالة مناسبة، وعدم فقدان النسخة المحلية.
6. تغيير جهاز جديد وتسجيل الدخول → استعادة كاملة للبيانات.
7. تكرار المزامنة عشر مرات → لا تتكرر المصاريف والمهام.

**هام قبل التطوير:** خذ Export لبيانات تجريبية، وخزّنها في مكان آمن خارج المتصفح.

## 9) PWA — تثبيت التطبيق والأوفلاين

في `manifest.json`:
- `lang: ar` و`dir: rtl` و`display: standalone`.
- أيقونات وأربع shortcuts: الصلاة، المصروف، الملاحظات، المهام.

في `sw.js` وقت المراجعة:
- Cache النسخة الحالية: `yawmi-v186`.
- ملفات أساسية تُخزّن عند التثبيت.
- **Network-first** لطلبات نفس الـorigin، ثم fallback للكاش.
- **Cache-first** لخطوط Google.
- طلبات Supabase وخدمات خارجية لا يخزّنها Service Worker بهذه الاستراتيجية.
- التعامل مع الضغط على الإشعار لفتح التطبيق/الرجوع إلى نافذته.

**مخاطر للمتابعة:** stale content، تنظيف caches القديمة، رسائل التحديث، سلوك فشل تثبيت الكاش، واختبار نسختين متتابعتين على الموبايل.

## 10) التذكيرات والإشعارات

`startReminderScheduler()` يعمل فحصًا كل دقيقة عبر `setInterval(checkDueReminders, 60000)`. التذكيرات المسجّلة تتضمن الصلاة والأذكار والقرآن والمراجعة والصيام وبعض الالتزامات.

**قيد مهم جدًا:** ده Scheduler **داخل الصفحة**؛ لا يضمن إرسال التذكير في الموعد لو التطبيق مغلق أو نظام التشغيل علّق التبويب. استدعاء `showNotification()` بواسطة Service Worker لا يعني أن فحص المواعيد نفسه يعمل في الخلفية. لو عايز تنبيهات موثوقة في الخلفية فده مشروع منفصل يتطلب تصميم Push/Backend، أذونات واختبارات لكل منصة.

## 11) التصميم وAccessibility

- RTL عربي، ألوان وثيمات مبنية على CSS custom properties.
- خطوط عربية متعددة، تحكم في حجم النص، دعم light/dark.
- Mobile-first مع media queries للديسكتوب.
- يوجد دعم `prefers-reduced-motion` في CSS.

**اختبارات موصى بها:**
- لوحة المفاتيح، ترتيب الـfocus، وضوح الـlabels و`aria-*`.
- التباين وحجم الخط، خصوصًا 200% zoom.
- VoiceOver/TalkBack، الشاشات الصغيرة جدًا.
- التصفح بالعربية وخلط الأرقام/العملات الإنجليزية مع RTL.
- قابلية سحب/ترتيب المهام بدون لمس (keyboard alternative).

## 12) Security & Privacy — نقاط فحص قبل الإنتاج

1. **Supabase RLS:** التأكد أن كل صف في `yawmi_data` مقيد بـ `auth.uid() = user_id` في عمليات select/insert/update/delete. ده **فحص مطلوب** وليس ادعاء بأن RLS غائب.
2. **DOM Injection / XSS:** توجد مواضع تبني HTML باستخدام `innerHTML` وtemplate strings من بيانات مثل أسماء تصنيفات المستخدم. لازم مراجعة escaping وDOM APIs، خصوصًا البيانات المحفوظة والمتزامنة.
3. **Local PIN:** قفل واجهة، لا يعادل تشفير LocalStorage ولا حماية ضد شخص يتحكم في الجهاز/المتصفح.
4. **Recovery:** اختبار Export/Import قبل ترحيل الـschema، وما نعتمدش على نسخة localStorage الوحيدة.
5. **CSP/Dependencies:** تقييم سياسة Content Security Policy، وتحميل الموارد الخارجية من CDN، وتثبيت الإصدارات/بدائل الاستضافة.
6. **Data minimization:** اليوميات والعادات والمصاريف بيانات شخصية؛ راجع الخصوصية ومدة الاحتفاظ ومسح الحساب والبيانات.

ده **هيكل مقترح** ومش معنى كده إننا نحتاج React أو TypeScript دلوقتي. ممكن نعمل Refactor تدريجي باستخدام **native ES modules** ونضيف الاختبارات بالتدريج.

### قواعد آمنة أثناء الـRefactor
- **لا تغيّر Data Keys** ولا شكل البيانات في أول مرحلة.
- **لا تغيّر حساب النتيجة** حتى لو فيه edge cases؛ وثّقه واختبره قبل اتخاذ قرار جديد.
- **لا تجمع نقل الكود مع إضافة features** في نفس PR.
- خذ Export تجريبي، وأجرِ smoke tests بعد كل وحدة.
- ضع قاعدة واضحة للتعامل مع تعارض بيانات الأجهزة، ثم اختبرها قبل تعديل sync.
- لا تدفع مفاتيح سرية مثل `service_role` للواجهة أو GitHub. مفاتيح publishable فقط مسموحة للعميل.
