# Yawmi — Technical Debt & Development Roadmap

> **الغرض:** قائمة تحسينات مرجعية ترجع لها لما تقرر تطور التطبيق.  
> **المراجعة:** 2026-11-16 — مبنية على قراءة ملفات المشروع الحالية، **مش نتائج اختبار شامل**.  
> **المبدأ:** حماية بيانات المستخدم قبل تغيير المعمارية.  
> **الدليل:** [TECHNICAL_GUIDE.md](./TECHNICAL_GUIDE.md)

## طريقة استخدام الملف

- **P0 / Risk:** احسمها قبل أي تغيير كبير ممكن يفقد بيانات.
- **P1 / Maintainability:** خطوات تسهّل صيانة المشروع واختباره.
- **P2 / Quality:** تحسينات مهمة بعد تثبيت الأساس.
- **Later / Product:** قرارات مستقبلية لا تتطلب تنفيذًا حاليًا.

كل بند له **المشكلة → الإجراء → معيار القبول**. ما تعتبرش أي مهمة منجزة لمجرد وجود الدالة؛ لازم تجربة أو Test.

## P0 — سلامة البيانات والأمان

### [ ] P0-01 — التحقق من Supabase RLS والصلاحيات

**لماذا؟** التطبيق يتعامل مع يوميات ومصاريف ومعلومات شخصية، والواجهة تستخدم publishable Supabase key. المفتاح العام مش سر، لكن لازم صلاحيات قاعدة البيانات تكون صحيحة.

**نفّذ:**
- راجع الـtable `yawmi_data` وسياسات RLS من Supabase Dashboard.
- تأكد أن `auth.uid() = user_id` تقيد كل عملية مسموحة بالمستخدم الحالي.
- جرّب بحسابين تجريبيين A وB، وحاول الوصول لبيانات B من A.
- راجع سياسة الحذف ومسح الحساب/البيانات.

**Done when:** حساب A لا يمكنه قراءة أو تغيير أو حذف صف B؛ اختبارات select/insert/update/delete موجودة وموثقة.

### [ ] P0-02 — Backup & Restore حقيقي قبل أي ترحيل

**لماذا؟** LocalStorage عرضة للمسح أو تضارب النسخ المحلية والسحابية.

**نفّذ:**
- صدّر عينة فيها يوميات، مهام، أهداف، مصاريف، التزامات، ملاحظات وتحديات.
- استوردها في بيئة اختبار منفصلة وقارن الأعداد والمحتوى.
- اختبر التصدير والاستيراد بعد Refresh.
- اختبر الرفض الآمن لملف JSON تالف أو شكل بيانات غير متوقع.
- أضف حقل schema version في خطة الترحيل المستقبلية، **دون تعديل بيانات الإنتاج في هذه المرحلة**.

**Done when:** النسخة المستعادة متطابقة، والملف التالف لا يمسح البيانات الحالية.

### [ ] P0-03 — اختبارات تعارض المزامنة

**لماذا؟** `syncPull()` + الدمج + `syncPush()` تتعامل مع تغييرات متزامنة من أكثر من جهاز.

**نفّذ:**
- Add/Add لمهام مختلفة على جهازين بدون إنترنت.
- Edit/Edit لنفس اليوم أو العنصر.
- Delete/Edit لنفس المهمة.
- مزامنة وقت فشل الإنترنت أو انتهاء جلسة Auth.
- تشغيل المزامنة المتكرر بدون duplicates.
- التأكد من حفظ backup قبل الدمج ومن عدم الرفع إذا فشل السحب.

**Done when:** كل سيناريو له سياسة دمج متفق عليها ونتيجة قابلة لإعادة الإنتاج؛ مفيش فقد أو تكرار غير متوقع.

### [ ] P0-04 — فحص حقن HTML داخل الواجهة

**لماذا؟** `innerHTML` يستخدم في مواضع تحتوي على قيم يُدخلها المستخدم، مثل أسماء التصنيفات؛ لازم منع تعامل النص كـHTML.

**نفّذ:**
- احصر أماكن استخدام `innerHTML` مع بيانات مرنة.
- استبدل إدراج النصوص بــ `textContent` و`createElement` عند الإمكان.
- لو لازم HTML، استخدم escaping/sanitization مدروسة ومختبرة.
- اختبر أمثلة مثل `<img src=x onerror=alert(1)>` في بيئة اختبار فقط، دون استخدام بيانات إنتاج.

**Done when:** المدخلات التي تشبه HTML تظهر كنصوص عادية، والـDOM لا ينفذ محتواها.

## P1 — تنظيم الكود والاختبار

### [ ] P1-01 — Baseline / نقطة مرجعية ثابتة

**نفّذ:**
- سجّل نسخة Git/commit قبل الـRefactor.
- اكتب خطوات تشغيل localhost.
- احتفظ بنسخة backup تجريبية.
- نفّذ **Smoke Test Checklist** في [TECHNICAL_GUIDE.md](./TECHNICAL_GUIDE.md#15-smoke-test-checklist--قبل-وبعد-أي-تغيير).
- دوّن المشاكل الموجودة مسبقًا عشان ما ننسبهاش للنقل.

**Done when:** كل تغيير لاحق سهل مقارنته بنفس نقطة البداية.

### [ ] P1-02 — اختبارات للدوال الحسابية النقية

**ابدأ بـ:**
- `scoreOf()`: صفر/كل الصلوات، عادات صفر/بعضها/كلها، rounding.
- `goalPct()`: هدف بدون مشاريع، مشروع واحد، عدة مشاريع.
- أرقام/عملات المصاريف وإجماليات الشهور.
- تنسيق التواريخ حول آخر الشهر وتغيير السنة.

**Done when:** نفس النتائج القديمة محفوظة، وأي تغيير مقصود في القواعد مصحوب بتعديل اختبار موثق.

### [ ] P1-03 — استخراج CSS من `index.html`

**نفّذ:**
- انقل الـCSS إلى `src/styles/` أو `styles/` بملفات قليلة في البداية.
- احتفظ بنفس ترتيب القواعد والـmedia queries.
- قارن light/dark وmobile/desktop بصور قبل/بعد.

**Done when:** لا يوجد اختلاف بصري غير مقصود.

### [ ] P1-04 — استخراج Utilities / Domain Logic

**الترتيب:** دوال تنسيق التاريخ والعملات → دوال درجات اليوم → حسابات الأهداف والمصاريف. تجنّب نقل الكود المتعلق بالـDOM في نفس PR.

**Done when:** كل وحدة export/import واضح، ونتائج الـtests كما كانت.

### [ ] P1-05 — فصل التخزين عن الواجهة

**نفّذ:**
- واجهة واضحة للقراءة والكتابة والتعامل مع JSON invalid.
- توحيد إدارة المفاتيح والـtimestamps.
- توثيق الـdata schema المبدئي.
- تجنّب تغيير أسماء المفاتيح أو البيانات المحفوظة في نفس PR.

**Done when:** الواجهات لا تتعامل عشوائيًا مع LocalStorage، والبيانات القديمة ما زالت تُقرأ.

### [ ] P1-06 — فصل الخدمات والـViews

**نفّذ:**
- `services/supabase.js`, `services/sync.js`, `services/prayer-times.js`, `services/notifications.js`.
- `views/today.js`, `views/tasks.js`, `views/goals.js`, `views/expenses.js`, `views/notes.js`, `views/dashboard.js`.
- خطوة واحدة لكل PR، وخلي الـrender functions تتعامل مع dependencies واضحة.

**Done when:** الوظائف تعمل كما كانت والتطبيق لا يعتمد على متغيرات global غير موثقة قدر الإمكان.

### [ ] P1-07 — اختبارات End-to-End + CI

**نفّذ:**
- أتمتة زيارة الصفحة وإضافة مهمة وتعديل إعداد وتسجيل مصروف.
- اختبار offline/online وService Worker على متصفح مدعوم.
- GitHub Actions: اختبار وLint قبل الدمج.

**Done when:** PR يفشل تلقائيًا عند كسر مسار استخدام أساسي.

## P2 — الأداء وتجربة الاستخدام

### [ ] P2-01 — سياسة تحديث PWA

- اختبر تحديث نسختين متتاليتين للـService Worker.
- وضّح للمستخدم توفر تحديث جديد دون إجباره على فقدان بيانات/تغييرات.
- راجع الكاش، أول زيارة بدون إنترنت، والعمل بدون API.

**Done when:** تحديث جديد يُطبّق دون فقد بيانات وتجربة التحديث موثقة على Android وiOS.

### [ ] P2-02 — Accessibility

- تنقل كامل بالكيبورد وfocus واضح.
- أزرار بأسماء accessible وحقول بنماذج صحيحة.
- contrast وحجم خط مناسب و200% zoom.
- مراجعة RTL وVoiceOver/TalkBack.

**Done when:** الإجراءات الأساسية ممكنة بدون استخدام الماوس أو اللمس.

### [ ] P2-03 — رصد أخطاء وتحسين أداء

- راجع أخطاء Console وطلبات Network الفاشلة.
- قِس performance على موبايل متوسط وضعيف.
- ابحث عن القوائم التي يعاد Render لها كلها عند كل تعديل.
- راقب حجم Cache ومشاكل مصادر الخطوط/CDN.

**Done when:** عندك قياسات قبل/بعد ويمكن إثبات التحسن بالأرقام.

## Later — قرارات منتج مستقبلية (اختيارية)

### [ ] L-01 — Notifications موثوقة في الخلفية

النظام الحالي يفحص المواعيد داخل الصفحة كل دقيقة. **لا تَعِد المستخدم بإشعار دائمًا والتطبيق مغلق**.

قبل التنفيذ قرر:
- هل تحتاج Push API وخادم يرسل التذكيرات؟
- التوافق مع Safari/iOS وAndroid؟
- المنطقة الزمنية والتوقيت الصيفي؟
- أذونات المستخدم والإلغاء والتكرار؟

### [ ] L-02 — Data export / التقارير

- تقارير شهرية قابلة للتصدير.
- نسخة backup ذات schema version.
- آلية حذف أو نقل بيانات المستخدم وفق احتياجات الخصوصية.

### [ ] L-03 — اختيار Framework

مش مطلوب لمجرد أن الملف كبير. ابدأ ES Modules. فكّر في Vite/TypeScript/Framework لاحقًا لو هتضيف فريق أو هتحتاج تنظيمًا أكبر، **بعد** تثبيت الاختبارات واستقرار البيانات.

## قواعد العمل من هنا ورايح

1. **PR واحدة = تغيير محدد**. لا تنقل كود وتضيف عشر مميزات مرة واحدة.
2. لازم **Backup + Tests** قبل أي تغيير في الـstorage أو الـsync.
3. كل قرار تقني مهم يتسجل هنا في سطرين: *ليه؟ وإيه بدائله؟*
4. لا تدمج برنش التوثيق عشوائيًا مع إعادة هيكلة التطبيق. هو مرجع؛ نقل الكود يتم لاحقًا في برنشات منفصلة.
5. عند إنهاء أي مهمة، حوّل `[ ]` إلى `[x]`، واكتب PR/commit المرجعي.

**الحالة الحالية:** جميع البنود أعلاه **مقترحات وتحقق مطلوب** — لا تدّعي أن تنفيذها تم.
